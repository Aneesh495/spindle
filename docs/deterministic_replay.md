# Deterministic Replay & Event Sourcing in Spindle

Deterministic replay is the foundational principle underlying durable workflow orchestration. This document details the mathematical invariants, state reconstruction algorithms, and non-determinism isolation mechanisms implemented in Spindle.

---

## 1. The Deterministic Replay Invariant

In standard programming models, if a process crashes mid-execution, its volatile heap state is lost. Traditional recovery approaches rely on periodically saving monolithic process snapshots (expensive and non-portable) or executing distributed two-phase commits (high latency and deadlock risks).

Spindle achieves fault-tolerance through **event sourcing**:
Every side effect (scheduling an activity, firing a timer, signaling an external system) is recorded as an immutable, append-only event in a Write-Ahead Log (WAL).

$$\text{State}_N = \text{Fold}(\text{InitialState}, [\text{Event}_1, \text{Event}_2, \dots, \text{Event}_N])$$

When a workflow worker resumes execution after a crash or failover:
1. It reads historical events from storage.
2. It re-executes the workflow code from the very beginning.
3. When the code requests an external action (such as executing an activity), the engine intercepts the call and checks history.
4. If a corresponding `ActivityTaskCompleted` event already exists in history, the engine immediately returns the recorded result without re-executing the external activity.
5. The workflow advances instantaneously to the point of interruption.

---

## 2. Eliminating Sources of Non-Determinism

For replay to work correctly, workflow code must be a pure, referentially transparent function of its event history. Spindle enforces strict boundaries to eliminate all sources of non-determinism:

### 2.1 System Clock Isolation
* **Problem**: Calling `DateTime.UtcNow` during replay produces different timestamps on every run, breaking time-dependent branch logic.
* **Solution**: Workflows must use `Workflow.now`. During replay, `Workflow.now` returns the deterministic timestamp recorded in the current `WorkflowTaskStarted` journal event.

### 2.2 Activity Identifier Monotonicity
* **Problem**: In concurrent or branched workflows, activity identifiers must match precisely between the first execution and subsequent replays.
* **Solution**: Spindle utilizes an explicit `DeterministicCounter` threaded through the `ExecutionContext`. Activity IDs are generated deterministically as `act-1`, `act-2`, etc., strictly aligned with AST traversal.

### 2.3 Side-Effect Confinement to Activities
* **Problem**: Executing arbitrary HTTP requests, database writes, or thread sleeps directly inside workflow definitions violates replay safety.
* **Solution**: All side-effects are restricted to Activities (`Workflow.activity`). The workflow code only defines the orchestration graph; activities are executed asynchronously on worker nodes and their outcomes are durably committed to the WAL.

---

## 3. Replay Divergence Detection

If an engineer modifies workflow code in production (e.g., adding an activity call before an existing activity), existing in-flight workflows could diverge during replay.

Spindle guards against replay divergence via `Spindle.Engine.Determinism.DeterminismValidator`:
* As the workflow re-executes, every command generated by the computation expression is validated against the recorded event stream.
* If the workflow generates a `ScheduleActivity` command for activity `B`, but historical records show that activity `A` was originally scheduled at this sequence, the validator immediately halts execution with `NonDeterministicDivergence`.
* The workflow is suspended safely, preventing journal corruption or duplicate external side effects.
